# 🦀 DPI Detector (Native Rust Engine)

[![Language: Rust](https://img.shields.io/badge/Language-Rust_2021-DEA584.svg?logo=rust&logoColor=white)](https://www.rust-lang.org/)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Release](https://img.shields.io/badge/Release-v5.0.0--alpha.14-blue.svg)](https://github.com/Runnin4ik/dpi-detector/releases)
[![Telegram](https://img.shields.io/badge/Telegram-2CA5E0.svg?logo=telegram&logoColor=white)](https://t.me/DPI_detector)

Нативный инструмент для анализа цензуры и блокировок трафика на **чистом Rust**:

* **Никаких внешних зависимостей**: без сторонних рантаймов, без C/C++ библиотек и системного OpenSSL — только `rustls`, `ring` и `RustCrypto`.
* **Легковесный**: статический бинарник ≈3.9 МБ (4–6 МБ на роутерных сборках, UPX — ≈1.4 МБ), потребление оперативной памяти в работе — **3–6 МБ RAM**.
* **Максимальная кросс-платформенность**: нативная поддержка роутеров (MIPS, ARM), Windows (от Windows 7 до 11), Linux musl, macOS и Android (Termux).
* **Интерактивный TUI + Batch**: полноценное стрелочное меню в терминале и быстрый тихий запуск при передаче аргументов командной строки.

## 🛠️ Установка на роутеры (Keenetic / OpenWrt / Entware)

При запуске на роутере скрипт `install.sh`:
1. Автоматически находит директорию `/opt/bin` (Entware) и устанавливает бинарник туда (сохраняется после перезагрузки).
2. **Контролирует свободное место**: если на накопителе осталось `< 7 МБ`, скрипт автоматически скачивает компактную версию со сжатием UPX (~1.4 МБ вместо ~3.9 МБ), защищая роутер от переполнения Flash или `tmpfs`.
3. Заменяет файл атомарно (`.tmp.$$` -> `dpi-detector`) с проверкой архитектуры через `--version` (при сбое UPX автоматически переключается на стандартный бинарник).
4. Поддерживает принудительный выбор версии: `DPI_UPX=1` (компактная) или `DPI_UPX=0` (стандартная).
5. Поддерживает запуск напрямую через SSH:

```bash
# Установка и запуск меню
curl -fsSL https://raw.githubusercontent.com/Runnin4ik/dpi-detector/rust/install.sh | sh

# Повторный запуск после установки
/opt/bin/dpi-detector
```

  -p, --proxy <URL>              URL SOCKS5-прокси (socks5://127.0.0.1:1080)
  -c, --concurrency <N>          Лимит параллельных запросов

      --burst-timeout <SECONDS>  Тест 6: таймаут одного рукопожатия, секунды [по умолчанию: 8]

      --burst-tls <VERSION>      TLS для теста 6: 1.3+1.2 (предложение браузера, ответ должен быть 1.3)|1.3 (только 1.3)|1.2 (только 1.2) [по умолчанию: 1.3+1.2]
      --burst-alpn <PROTOCOL>    ALPN для теста 6: h2 (предлагает h2 с откатом на http/1.1)|http/1.1 (только http/1.1) [по умолчанию: h2]
      --trace [<PATH>]           Тест 6: трасса по строке на попытку (раунд, отпечаток, домен, статус, деталь, мс); без пути — в stderr, с путём — в указанный файл [по умолчанию: выключено]

Справка и все сообщения локализованы: `dpi-detector --lang en --help`, `--lang zh --help`, `--lang fa --help`. Язык интерфейса задаётся `--lang`, таблицы, легенда и предупреждения следуют за ним; Farsi выводится латиницей (Finglish). Статусные бейджи и имена протоколов (`OK`, `BLOCKED`, `TLS RST`, `SNI`, `ClientHello`) остаются латиницей в любом языке. Машинный вывод `--json` от языка не зависит.

### Номера доступных тестов:
* `0` — **Информация о сети и системе** (внешний IP, провайдер, AS, страна, тип NAT)
* `1` — **Доступность DNS-серверов** (проверка UDP 53, DoH Cloudflare/Google/Quad9/Yandex/AdGuard)
* `2` — **Доступность сайтов** (HTTP, TLS 1.2, TLS 1.3, классификация блокировок DPI)
* `3` — **Доступность CDN и хостингов (тест 16 KB)** (детект сброса соединений после 14–34 КБ данных)
* `4` — **Поиск белых SNI** (перебор рабочих SNI для заблокированных AS: цель отбирается по 16 KB-обрыву, TLS RST и TLS DROP)
* `5` — **Доступность Telegram** (проверка доступности и скорости датацентров DC1–DC5)
* `6` — **Fingerprint/Сибирская блокировка** (N накладывающихся TLS-рукопожатий на один домен выбранными отпечатками, старты через 20 мс: сколько ответили и на какой попытке включился блок)
* `7` — **Легенда статусов** (справка по вердиктам)

## 🧬 Тест 6: Fingerprint / Сибирская блокировка

Тест отвечает на вопрос «блокируют ли именно мою форму TLS-рукопожатия»: на каждый домен отправляются N попыток выбранными отпечатками, старты разнесены на 20 мс, и видно, какие формы ответили, а какие нет.

Триггер, который тест воспроизводит, следит за **частотой**: несколько попыток соединения внутри окна в пару сотен миллисекунд. Отсюда и 20 мс между стартами. Строго по одной попытке этот порог на медленном канале не достигается вообще: интервал между стартами там равен длительности предыдущей попытки (у меня на восьми хостах это 90–400 мс, то есть «три старта подряд» занимают от 220 до 750 мс — половина уже вне окна 250 мс). Залпом всего сразу — противоположная ошибка: все N успевают установиться до того, как блок ляжет, весь раунд проходит целиком, и блок видно только в следующем прогоне. 20 мс — компромисс: пять попыток укладываются в 80 мс (внутри любого разумного окна), но блок успевает лечь *между* двумя стартами, поэтому в отчёте видно, на какой именно попытке он включился. Домены при этом по-прежнему идут параллельно (их ограничивает `-c`).

Домены у теста свои: `burst-domains.txt` рядом с бинарником, в сборке — `realmeteo.ru`, `ezgame.su`, `scpslgame.ru`, `kyles.ru`, `amserg.com`, `smartape.ru`, `reg.ru`, `info.paymaster.ru`. Это обычные сайты, которые на первом соединении отвечают нормально: заблокированный сайт провалит все попытки по причине, которую тест не измеряет. Список теста `2` (`domains.txt`) остаётся списком заблокированных сайтов и к тесту `6` отношения не имеет; `-d` и `--domains` перебивают оба.

При выборе теста `6` открывается свой экран настроек: число соединений на домен, таймаут одного рукопожатия **в секундах**, **версия TLS** (`1.3+1.2` — предложение браузера, ответ должен быть `1.3`; `1.3` — только 1.3; `1.2` — только 1.2), **протокол HTTP в ALPN** (`h2` — как у браузеров, с откатом на `http/1.1`, или `http/1.1` — только он), домен (пустое поле — весь список теста `6`; вставленный URL приводится к имени хоста) и **Fingerprint** (по умолчанию все). Поле домена подсвечивается: серый фон — строка выбрана, синий — в поле идёт ввод. `Q`/`Esc` отменяет тест.

Попытка не заканчивается рукопожатием: сразу после него тем же профилем (и тем же `User-Agent`/заголовками) уходит `GET /` по тому протоколу, который выбрал ALPN. Попытка считается удачной, только если вернулся ответ — обрыв на запросе, редирект на чужой хост, `HTTP BLOCK` или таймаут чтения видны как своя строка, а не как «ответили». Редирект внутри своего сайта вердикта не меняет: основной домен, его поддомены и два поддомена одного домена — одна и та же площадка, поэтому `holod.media` → `www.holod.media`, `m.holod.media` → `holod.media` и `m.youtube.com` → `www.youtube.com` читаются как `OK`, а на чужой домен (`www.instagram.com` → `www.facebook.com`) — как `REDIR` с именем хоста в детали.

В таблице `M/N` по каждому отпечатку: зелёный — все попытки прошли целиком, жёлтый — часть, красный — никто. В колонке «Детали» — **все** вердикты строки, сгруппированные по статусу, самые частые первыми (`TLS ALERT ×8 · TLS RST ×4`), так что двенадцать потерянных рукопожатий не схлопываются в одну «победившую» ошибку. Номер попытки в трассе — это номер **старта**, а не завершения: попытки идут внахлёст, поэтому в отчёте видно, на какой именно из них включился блок (`2/5` — первые два соединения ответили, дальше перестало).

Раунд одной формы на одном домене — это N накладывающихся попыток, поэтому по времени он стоит примерно как одна: последний старт отстоит от первого на `(N−1) × 20` мс, и раунд заканчивается, когда завершится самая долгая попытка. При `--burst 5` и таймауте 8 это ~8.1 секунды на домен, а не 40, как было бы при строгой очереди. Домены идут параллельно, поэтому общее время прогона ≈ самое медленное домен-раунд, а не сумма.

Во время прогона печатается одна живая строка `Тестируем: CHROME 107 3/4  12/35 · 00:04` — какая форма сейчас в эфире, который это раунд из скольких, сколько хостов раунда готово и сколько идёт время.

Из неинтерактивного запуска настройки задаются флагами `--burst`, `--burst-timeout`, `--burst-profiles`, `--burst-tls`, `--burst-alpn`; в `--json` результат лежит в ключе `results.fingerprint_burst`.

### Трасса попыток (`--trace`)

`--trace [<PATH>]` пишет по строке на каждую попытку — время UTC, раунд, форма, домен, номер попытки, статус, деталь и миллисекунды:

```text
13:19:30Z  r1/1 chrome   www.google.com               #1  tls_alert    alert_unexpected_message                   719 ms
13:19:30Z  r1/1 chrome   standby-rezka.tv             #1  tls_alert    alert_illegal_parameter                   1031 ms
```

Без пути трасса идёт в stderr, с путём — в указанный файл: `--trace C:\temp\trace.log` и `Get-Content -Wait C:\temp\trace.log` во втором окне дают разбор прямо во время работы интерактивного меню. Видно, какая именно из N попыток, с какой задержкой и по какой причине не прошла — тишина до нашего таймаута, сброс за десятки миллисекунд или алерт от сервера.

Отдельно стоит знать про разбор провалившейся колонки: если попытки умирают с задержкой ровно в таймаут (8000 мс при `--burst-timeout 8`) у **всех** форм сразу, а быстрые хосты в том же раунде успевают ответить, — это провал пути, а не блокировка отпечатка. В замерах через VPN-тоннель целые раунды из 35 доменов умирали так двадцать-сорок секунд и так же сами восстанавливались, причём жертвой оказывалась то одна форма, то другая: при последовательных раундах такое окно целиком попадает в одну колонку и выглядит как её блокировка.

### Профили отпечатка (`--fingerprint`)

Профиль задаёт три слоя сразу — форму TLS-рукопожатия, `User-Agent` с набором и порядком заголовков и преамбулу HTTP/2, — и все три взяты из одного набора `curl-impersonate v2.2.2`, поэтому клиент, выглядящий как `curl_chrome107` в одном слое, выглядит так же и в остальных.

* `rustls` (по умолчанию) — контрольная форма: никого не изображает.
* `firefox` — Firefox 133, `chrome` — Chrome 107 / Edge 99-101, `safari` — Safari 15.5–18.4.

Два отличия от настоящих браузеров, о которых стоит знать при сравнении: ECH не отправляется (его синтез ломает рукопожатие с Google и Cloudflare), а `accept-encoding` всегда `identity` — тесты 2–4 считают байты до обрыва, и согласованное сжатие сделало бы эти числа зависящими от сжимаемости ответа. Свой `user_agent` в `config.yml` перебивает профиль.

У профиля `firefox` есть ещё два, оба в телах расширений и потому невидимые для JA3/JA4 и для `tls.peet.ws`: список алгоритмов сжатия сертификата короче на `zstd` (в сборке нет его распаковщика), а долей ключа две вместо трёх — у бандла третья, P-256. Оба видны только при побайтовом сравнении с `curl_firefox133`.

## 🏗️ Сборка из исходников

Для самостоятельной сборки потребуется установленный Rust (версии 1.80+):

```bash
git clone https://github.com/Runnin4ik/dpi-detector.git -b rust
cd dpi-detector
cargo build --release -p dpi-detector
```

Скомпилированный бинарник будет находиться в `target/release/dpi-detector` (`dpi-detector.exe` на Windows).

Для статической сборки под Windows без внешних зависимостей CRT:
```bash
RUSTFLAGS="-C target-feature=+crt-static" cargo build --release -p dpi-detector
```
