# План: расширение набора фингерпринтов (до десятков профилей)

Документ описывает, как добавлять новые TLS/HTTP-профили (более новые версии браузеров, Edge,
мобильные) без роста ручного кода пропорционально их числу, откуда брать данные и как каждый
профиль принимается в репозиторий.

Цель: **десятки профилей как данные, а не как код**, с оффлайновой верификацией (JA3/JA4-пины)
и одним и тем же набором приёмочных прогонов на каждый новый профиль.

Не-цели этого плана:

* HTTP/3 и QUIC — отдельный блокер: в `vendor/rustls-rustcrypto/src/quic.rs` стоит `todo!()`, а
  все TLS 1.3-сьюты объявлены `quic: None` (см. §10).
* ECH — нет HPKE в провайдере; профиль, которому ECH обязателен, пока не принимается (§6).
* Запись-уровневые трюки (дробление ClientHello по records, record size limit, middlebox CCS) —
  фиксируются как известное расхождение, но не воспроизводятся.

## 2. Почему «десятки» нельзя добавить в текущем виде

1. **Данные зашиты кодом.** Три билдера ≈ 100 строк каждый. Двадцать профилей — это ~2000 строк
   почти одинакового кода и двадцать мест, где можно ошибиться в одной константе.
2. **Строки i18n перечисляют профили.** `cli_fingerprint` и `warn_unknown_fingerprint` содержат
   «rustls|firefox|chrome|safari» — при N профилях это N×4 переводов и постоянный дрейф.
3. **Парсер знает про диапазоны версий вручную.** `curl_version()` (`:463`) плюс условия вида
   `version <= 107`, `matches!(version, 155|170|172|180|184)`.
4. **Нет машинного гейта «профиль ⊆ провайдер».** Сейчас проверяется только сжатие сертификата
   (`:1545`); что заявленный cipher/group/sig-alg провайдер действительно умеет — не проверяется.
5. **Тест 6 по умолчанию гоняет `ALL`.** N профилей × домены × 2 версии TLS — это сетевой бюджет,
   который растёт линейно и молча.

## 3. Целевая архитектура: профиль как данные

Разбить `net/fingerprint.rs` (1564 строки) на модули, сохранив публичный API:

```
net/fingerprint/
├── mod.rs        // TlsFingerprint, SPECS, parse/parse_list, apply, pinned_drop, гейты
├── shapes.rs     // SHAPES: &[TlsShape] — все данные профилей
├── h2.rs         // H2Fingerprint и таблица префейсов
├── identity.rs   // HttpIdentity: UA и заголовки
└── tests.rs      // пины JA3/JA4 и структурные тесты
```

Один профиль — одна запись данных:

```rust
struct TlsShape {
    code: &'static str,               // "chrome133" — JSON, конфиг, round-trip
    token: &'static str,              // "CHROME" — таблицы и логи (Rule 4)
    label: &'static str,              // "CHROME 133" — заголовки, где есть место версии
    family: Family,                   // Chrome | Firefox | Safari | Edge | Other
    source: &'static str,             // "curl_chrome133 (lexiforest v2.2.2)" — версия источника
    ciphers: &'static [u16],
    groups: &'static [u16],
    key_shares: &'static [u16],       // группы, для которых шлём шар (может быть ⊂ groups)
    sig_algs: &'static [u16],
    ext_order: &'static [Ext],        // с маркерами GREASE на своих позициях
    raw_exts: &'static [(u16, &'static [u8])],
    suppress: &'static [u16],
    alpn: &'static [&'static [u8]],
    versions: &'static [u16],         // supported_versions + legacy-фолбэки
    padding_to: Option<usize>,        // Chrome: Some(512)
    grease: bool,
    cert_compression: &'static [u16],
    pq: bool,                         // нужен провайдер с X25519MLKEM768
    aliases: &'static [&'static str], // "curl_chrome133", "chrome133"
}

static SHAPES: &[TlsShape] = &[ /* ... */ ];
```

`ClientHelloProfile` собирается из записи одним билдером; `SPECS`, `ALL`, `parse`, `parse_list`,
`h2_fingerprint()`, `http_identity()` и `needs_pq()` читают те же данные, а не свои `match`-ветки.
Правило: **вариант в `TlsFingerprint` без строки в `SHAPES` — ошибка компиляции/теста**, а не
тихий дефолт.

## 4. Откуда брать данные

| Источник | Что даёт | Как переносить |
|---|---|---|
| **uTLS** (refraction-networking, v1.8.2, янв 2026) | эталонные спеки hello: списки cipher suites, порядок расширений, curves, sig algs, ALPN; профиль Chrome 133 добавлен в v1.8.0 | механический перенос таблиц Go → `TlsShape`; источник **спеки**, не пруф |
| **lexiforest/curl-impersonate** v2.x (активный форк; оригинал `lwthiker` застыл на 2024-07-18) | эталонные JA3/JA4 и h2-захваты (`SSLKEYLOGFILE`) | эталон для пинов §5.3; версия бандла пишется в `source` |
| **bogdanfinn/tls-client** v1.16.0 (сен 2026) | широкий каталог по версиям, включая h2-профили | сверка h2-таблиц и «а есть ли вообще такой профиль» |
| **FoxIO JA4+** (Rust, активен) и база ja4db | сверка JA4, готовые описания «фич» hello | кросс-проверка пинов JA4 |
| Живой браузер + mitmproxy/Wireshark (`SSLKEYLOGFILE`) | «как реально шлёт» для новой версии | источник истины, когда библиотек под версию ещё нет |

У каждого профиля в `source` фиксируется, из какого релиза источника он снят: обновление
источника = осознанный пересмотр пинов, а не молчаливая смена формы.

## 5. Процедура добавления одного профиля

1. Запись в `SHAPES` + алиасы; `TlsFingerprint` расширяется тривиально.
2. Парсинг: алиасы и правила диапазонов — в данных; тест `fingerprint_parses_known_values_and_rejects_others`.
3. Пины `bundle_versions_match_their_ja3` / `_ja4`: **ожидаемые строки берутся из источника**, не
   из нашего же дампа (иначе тест закрепляет нашу ошибку). JA4 строже JA3: он хеширует
   `signature_algorithms` и ALPN — так у Safari нашлась отсутствовавшая `ecdsa_sha1`.
4. `cargo test -p dpi-core fingerprint`.
5. Дамп без сети: `cargo run --release --example tls_fingerprint dump <code>` (+ `dump12`, `dump13`) —
   глазами сверить порядок расширений, GREASE-позиции, padding.
6. Живой прогон: `live <code>` по базовым хостам, обязательно включая `hub.docker.com` и
   `danbooru.donmai.us` (добавляют SCT в certificate entry) и `standby-rezka.tv` (GREASE-шар;
   исторически отдавал fatal alert 12/12 без правильной формы).
7. HTTP/2: `tls.peet.ws` должен показать ожидаемый akamai-фингерпринт (порядок SETTINGS и
   псевдозаголовков этим и проверяется).
8. Регрессия: JSON тестов 1–6 для существующих `code` не изменился (на локальном стенде).
9. Если профилю нужно новое расширение — патч в `vendor/rustls` + строка в
   `vendor/rustls/README-PATCH.md` и пункт в `PATCH.diff`.

## 6. Машинные гейты (то, что должно падать само)

* **Профиль ⊆ провайдер.** Новый тест: для каждой записи `SHAPES` каждый cipher, group и
  sig-alg присутствует у провайдера (`cipher_suites`, `kx_groups`,
  `signature_verification_algorithms.all`), а каждый алгоритм сжатия проходит существующую
  проверку `cert_compression::covers`. Нарушение = либо не заявлять, либо дописать в провайдер
  (как `X25519MLKEM768` в `crates/dpi-core/src/net/pq_kx.rs`).
* **Группы vs шары.** Браузеры перечисляют в `supported_groups` больше, чем шлют шаром (например,
  P-521). Наш провайдер P-521 и DHE не умеет. Тест обязан проверять: каждая группа из
  `key_shares` обслуживается провайдером; группы «только в списке» допустимы, но тогда это
  осознанное решение и оно отмечено в `TlsShape` комментарием.
* **Версии.** Пин версии меняет `supported_versions` (документированное отклонение) — для профиля
  решается, нужны ли `legacy_versions`, и это закреплено тестом `grease_version_leads_supported_versions`.
* **ECH.** Профиль без ECH допустим, но это отражается в JA4 (счётчик на 1 меньше) и в комментарии.
  ECH — только в форме GREASE (см. §12): настоящий требует `ECHConfigList` из DNS целевого хоста,
  то есть является свойством хоста, а не клиента, и записи его не воспроизводят.
* **Сертификатные расширения.** SCT (18) — уже принимается; delegated credentials (34) — не
  поддерживаются, не заявлять.

## 7. Масштабирование интерфейса и бюджета

* Ввести `DEFAULT_SET` (5–8 профилей) и `ALL` (всё, только по явному запросу). Тест 6 по умолчанию
  ходит по `DEFAULT_SET`; JSON и таблица показывают только выбранное.
* i18n: перестать перечислять профили в `cli_fingerprint` и `warn_unknown_fingerprint`
  (Rule 6 — строки остаются в i18n, но без списка имён: список генерируется из `SPECS`).
* `--legend`: добавить таблицу профилей, собранную из `SPECS` (лейблы латиницей, Rule 4).
* Бюджет прогона: N профилей × домены × 2 версии; зафиксировать в README ориентир по времени для
  `DEFAULT_SET` и предупреждение для `ALL`.
* JSON: `fingerprint_burst` уже ключуется `code` — расширение аддитивно и схему не ломает (Rule 5).

## 10. Что осталось за границей этого плана

QUIC/HTTP/3: в `vendor/rustls-rustcrypto/src/quic.rs` — заглушка (`todo!()` в
`encrypt_in_place`/`decrypt_in_place`), все TLS 1.3-сьюты `quic: None`. Пока это так, ни один
HTTP/3-профиль невозможен, независимо от наличия `quinn`/`h3`. Порядок работ для него: (1) QUIC
header protection по RFC 9001 §5.4 с тест-векторами §A.2, (2) `quinn` без дефолтного `rustls-ring`
+ `h3`, (3) патч transport parameters (в quinn они жёстко зашиты), (4) фича `http3`, по умолчанию
выключенная (Rule 2).

## 11. Definition of Done для «профиль добавлен»

* Запись в `SHAPES` с `source` и алиасами; `parse` принимает канонические и `curl_*` имена.
* Пины JA3 **и** JA4 из источника; `cargo test -p dpi-core fingerprint` зелёный.
* `dump`/`dump12`/`dump13` совпадают с источником; `live` проходит по базовым хостам + SCT-хосты +
  `standby-rezka.tv`; `tls.peet.ws` показывает ожидаемый akamai-фингерпринт.
* JSON существующих профилей не изменился; `cargo test --workspace` и
  `cargo clippy --workspace --all-targets -- -D warnings` чисто.
* Обновлены `--legend`/README-упоминания, если профиль попадает в `DEFAULT_SET`.

## 12. Состояние на 2026-09-18

Сделано в этом репозитории:

* **M2 (данные вместо кода).** `net/fingerprint.rs` разбит на
  `net/fingerprint/{mod,shapes,h2,identity,tests}.rs`. Профиль — запись в
  `SHAPES`: имена и алиасы, правила `curl_*`, `source`, TLS-списки, гейты `pq`

  `apply`, `pinned_drop`, `hello_profile` и `--legend` читают таблицу;
  `TlsFingerprint::ALL` — единственный рукописный список, и
  `fingerprint_table_is_total` сверяет его с таблицей в обе стороны.
  Байты четырёх прежних профилей не изменились: пины JA3/JA4
  (`bundle_versions_match_their_ja3` / `_ja4`) те же, JSON тестов 1–6 — тот же.
* **M1 (новые профили).** `chrome133` (`curl_chrome133a` v2.2.3 + uTLS
  `HelloChrome_133` v1.8.2), `safari18` (`curl_safari180`) и `edge101`
  (`curl_edge101` + uTLS `HelloEdge_106`).
  * Edge и Safari 18 называют те же TLS-списки, что `chrome` и `safari`: у
    бандла тот же JA3 (`safari_18.0_macOS` публикует `ja3_hash`
    `773906b0efdefa24a7f2b8eb6985bf37`, его же вернул `tls.peet.ws`), поэтому
    их пины — пины старших записей, а `profiles_that_share_a_tls_shape_send_the_same_hello`
    это фиксирует. Отличаются identity и преамбула h2.
  * Chrome 133 — отдельная форма: `X25519MLKEM768` первым (и в списке, и
    шаром), ALPS на новом кодпойнте 17613, без padding. Опубликованный
    `ja3_text` бандла для 133 снят с базы Chrome 131 (файл сам это оговаривает)
    и расходится с обёрткой по кодпойнту ALPS, поэтому порядок расширений взят
    из uTLS, ECH опущен (как у `firefox`), а JA4 пинится по частям: счётчики и
    хеш шифров (`8daaf6152771` — публикуемый для Chrome 133+) из источника,
    хеш расширений — наш (`_LESS_ECH`).
  * Живые прогоны: `liveany chrome133` и `liveany safari18` проходят на
    `tls.peet.ws`, `cloudflare.com`, `www.google.com`, `www.wikipedia.org`,
    `www.microsoft.com`, `dns.google`, `hub.docker.com`, `danbooru.donmai.us`;
    `peet` подтверждает akamai-фингерпринт преамбул (`1:65536;2:0;4:6291456;6:262144|…`
    у 133, `2:0;3:100;4:2097152|10420225|0|m,s,p,a` у Safari 18).
* **M3 (гейты).** `every_advertised_code_point_is_served_or_named`: каждый шифр,
  группа и схема подписи каждого профиля либо обслуживается провайдером, либо
  назван в `UNIMPLEMENTED` с причиной, и наоборот — устаревшая запись валит
  тест. `the_advertised_group_list_opens_with_the_group_we_share` требует, чтобы
  список групп открывался той группой, которой профиль шлёт шар
  (`initial_key_share` берёт первую группу провайдера). Плюс

### Сквозная проверка всех девятнадцати (2026-09-18)

Проверка M4 «на глаз» опиралась на выборку: JA3/JA4 и тела расширений сверялись
для новых записей, а h2 — для трёх профилей из семи старых. Полный прогон по
всем записям сразу (три независимых сравнения, `tools/fingerprint/`) нашёл одну
настоящую ошибку и подтвердил остальное.

**Ошибка: порядок псевдозаголовков у Safari 18 и 26.** `SAFARI18_H2` и
`SAFARI260_H2` отправляли `:method, :scheme, :path, :authority` (`m,s,p,a`), тогда
как и обёртка (`--http2-pseudo-headers-order "msap"`), и захват форка
(`safari_18.0_macOS.yaml`: `pseudo=method,scheme,authority,path`), и сам бандл на
проводе отправляют `m,s,a,p`. Порядок псевдозаголовков не видит ни один хеш
ClientHello, а сэмпловые тесты пинили его только для `chrome`, `firefox` и
`safari` 15.5 — то есть для трёх записей из девятнадцати. Исправлено; теперь это
пинет один сплошной тест `every_h2_preface_matches_the_wrapper_it_copies`
(настройки с их порядком, окно, порядок псевдозаголовков и приоритет для каждой
записи с преамбулой), и он падал на старом значении.

Чем измерено:

* **Байты рукопожатий.** Оба клиента идут на один локальный слушатель с одним
  SNI (`localhost`), затем сравниваются тела всех расширений, длина padding,
  список сжатия, доли ключа. Побайтово совпали девять записей: `chrome`,
  `safari`, `safari18`, `edge101`, `chrome99android`, `safari153`,
  `safari184ios`, `safari260`, `safari260ios` (517/517, 1536/1536 байт).
  Остальные отличаются только перечисленным ниже.
* **Эхо-сервис** (`tls.peet.ws/api/all`), оба клиента по очереди: JA3, JA4,
  peetprint, Akamai-отпечаток h2, **каждый кадр** преамбулы (SETTINGS с
  порядком, WINDOW_UPDATE, флаги и приоритет HEADERS) и список заголовков
  запроса. Совпало всё, кроме ECH-хешей и настроек `8:1`/`9:1`.
* **Захваты форка** на теге бандла (`v2.2.2`): шифры, список расширений, группы,
  доли ключа, JA4. Совпало у всех, кроме тех же ECH и долей ключа.
* **Блок HTTP/1.1-запроса** (локальный TLS-слушатель, только `http/1.1`): строка
  запроса, имена заголовков с регистром, их порядок и значения. Строка запроса и
  порядок совпали везде; набор и значения — тоже, кроме одного случая; имена —
  только у тех записей, чья обёртка сама написана в нижнем регистре.

Намеренные отличия, которые прогон оставляет (и почему):

| Отличие | Записи | Причина |
|---|---|---|
| порядок расширений — своя выборка | хромы 110+ | клиент перемешивает расширения каждое соединение, и сборка тоже; совпадает только JA4, а JA3 у обеих сторон новый на каждом соединении |
| под 512 байт padding не отправляется | `chrome120`, `chrome131android` | у клиента с самым коротким телом GREASE-ECH hello опускается до 497 байт и он паддит его до 517; слот padding в записи перелетает — `padding_to` меряется до того, как rustls допишет типизированное тело ECH, — поэтому шлётся вариант без padding, который сам клиент шлёт в трёх соединениях из четырёх |
| долей ключа больше, чем в захвате браузера | `tor145` | запись следует своей обёртке (`--tls-key-shares-limit 3` — три доли), а не самому браузеру в захвате форка, где их меньше |

Строки про настройки `8:1`/`9:1`, регистр имён заголовков и `priority` в h1 из этой
таблицы убраны: они закрыты патчами `h2`/`hyper` и картой регистра в
`probe::http::header_case_map`, и прогон это подтверждает — `headers-diff` совпадает
побайтово у всех восемнадцати записей (включая длины блоков), `echo-diff` совпадает
по каждому кадру преамбулы, включая Safari 18 и 26 с их `8:1`/`9:1`.

Чем закрываются (если понадобится 100% соответствия) — список на момент того
прохода; всё, кроме настоящего ECH, с тех пор закрыто, см. разделы ниже:

* **`8:1`/`9:1`** — сеттеры в `h2` **и** `hyper` (шаблон уже есть: так проведён
  `settings_order`), затем перегенерация обоих `PATCH.diff`. Новых зависимостей
  нет, обе книги уже вендорены. **Закрыто** — см. «Закрытие четырёх зазоров».
* **`zstd` в `compress_certificate`** — нужен чистый Rust-декодер (например
  `ruzstd`) в `net/cert_compression.rs`: заявлять алгоритм, который не сможем
  распаковать, нельзя (сервер выберет его и рукопожатие упадёт). Цена — размер
  бинарника и память (Rule 2), зависимость чистая (Rule 1).
* **Третья доля ключа** — хук в `rustls` (`client/hs.rs` собирает ровно одну
  долю плюс гибридную компоненту): «слать доли первых N групп из списка».
  Средний патч, без новых зависимостей.
* **Регистр имён в h1** — `hyper` уже умеет писать исходный регистр
  (`encode_headers_with_original_case`), но `HeaderCaseMap` — `pub(crate)`;
  нужен маленький патч (сделать тип публичным) плюс исходный регистр в
  `identity.rs` (сейчас таблицы в нижнем регистре). Новых зависимостей нет.
* **ECH** — настоящий, а не синтезированный: взять `ECHConfigList` из DNS
  (HTTPS/SVCB — модуль уже есть), шифровать внутренний hello через HPKE. Тело
  расширения всё равно своё на каждом соединении, так что побайтового равенства
  с бандлом не даст, но счёт расширений, JA3/JA4 и поведение с ECH-серверами
  станут как у оригинала. Большая работа.
* **Порядок расширений Chrome 110+** — воспроизвести перемешивание Chromium
  (какие расширения фиксированы, какие тасуются) в патче rustls. Побайтового
  равенства не даст *никогда*: у настоящего Chrome форма меняется от соединения
  к соединению, сравнивать можно только распределение.

Инструмент проверки лежит в `tools/fingerprint/` (`fingerprint.py` + README): он
же печатает таблицу флагов обёртки (`flags <профиль>`) — то есть служит и
источником данных для новой записи, а не только проверкой.

### Закрытие четырёх зазоров (2026-09-18)

Из таблицы выше закрыты все, кроме ECH, `zstd` и перемешивания расширений —
то есть всё, что закрывается патчем или данными.

* **Настройки `8:1` и `9:1`** (`SETTINGS_ENABLE_CONNECT_PROTOCOL`,
  `SETTINGS_NO_RFC7540_PRIORITIES`). Патч `h2`: id 9 проведён целиком (поле,
  вариант `Setting`, разбор, кодирование, `Debug`), а setter для id 8 был только
  у серверного билдера — добавлен клиентский. Патч `hyper` — два поля в
  `proto::h2::client::Config` и два сеттера на `client::conn::http2::Builder`
  (шаблон тот же, что у `settings_order`). Данные: `safari18` шлёт `8:1;9:1`,
  `safari184ios`/`safari260`/`safari260ios` — только `9:1` (и обёртка, и захват
  форка говорят одно и то же: у iOS-сборки 18.4 настройки `8` нет вовсе).
* **Регистр имён заголовков в HTTP/1.1.** hyper умел писать исходный регистр с
  0.12 (`write_headers_original_case`), но `HeaderCaseMap` был `pub(crate)`;
  патч делает тип и его `default`/`append` публичными. Данные: имена в
  `identity.rs` теперь записаны так, как их пишет клиент (`Sec-Fetch-Site`,
  `Accept-Encoding`, `TE`, `Te` у `curl_firefox144` — у него обёртка однострочная,
  а бандл пишет `Te`; и всё в нижнем регистре у `safari18` и новее), а
  `probe::http` собирает из них карту и кладёт в расширения запроса. `Host`
  добавляет билдер — в карте он записан с большой буквы, как у curl.
* **`priority` в h1.** Обёртки называют `-H "Priority: u=0, i"` у всех, но curl
  кладёт его на провод только для Firefox и Tor (измерено по захваченным
  запросам бандла), поэтому признак `TlsShape::priority_on_h1` — данные записи,
  а не правило по семейству: у четырёх записей он `true`, у остальных заголовок
  уходит только в h2, как у бандла.
* **Доли ключа.** `rustls` получил `ClientHelloProfile::key_share_groups`:
  список групп, для которых шлётся доля, вместо одного выбора («первая группа
  плюс гибридная компонента»). `offered_key_share` стал списком exchange'ов,
  а выбор при `ServerHello` и в обработке HelloRetryRequest ищет группу сервера
  по всем отправленным долям. Данные: Firefox — `[X25519MLKEM768, secp256r1]`
  (три доли на проводе, компонента гибрида входит в первую), Tor —
  `[X25519, secp256r1, secp384r1]`.

Проверено тем же прогоном: `hello` — у Firefox впервые совпали доли ключа, у
Tor впервые совпало всё, кроме ECH; `echo-diff` — у всех четырёх Safari-записей
Akamai-отпечаток теперь совпадает байт в байт (включая `8:1`/`9:1`), `headers-diff`
— все восемнадцать записей совпадают по регистру, порядку и значениям, включая
`Host` и `priority`. Патчи (`vendor/{h2,hyper,rustls}/PATCH.diff`) перегенерированы
и проверены: применяются к чистым исходникам crates.io и дают дерево, совпадающее
с `vendor/` (`742`, `170`, `1103` строки). Тесты — `cargo test --workspace`
(173 + 58) и `clippy` без предупреждений; новые пины:
`every_h2_preface_matches_the_wrapper_it_copies` (расширен на `8:1`/`9:1`),
`every_identity_is_spelled_the_way_its_client_writes_it`,
`every_profile_sends_the_key_shares_its_wrapper_asks_for`, плюс два теста
`probe::http` на карту регистра и на `priority`.

Что осталось: ECH (нужен настоящий HPKE с `ECHConfigList` из DNS), `zstd` в
`compress_certificate` (нужен чистый Rust-декодер), перемешивание расширений у
Chrome 110+ (воспроизводить распределение — отдельная работа, и побайтового
равенства она не даст), и у `tor145` на одну долю больше, чем у браузера в
захвате форка (запись следует своей обёртке).

### ECH, `zstd` и перемешивание расширений (2026-09-18)

Закрыты три из четырёх оставшихся пунктов — всё, что не требует DNS-запроса к
самому хосту.

* **Перемешивание расширений.** Chromium 110+ тасует порядок расширений каждое
  соединение: `ssl_setup_extension_permutation` в BoringSSL — один проход
  Фишера–Йетса по таблице расширений с зёрнами из `RAND_bytes`, а GREASE и
  padding добавляются вне этого цикла; `SSL_set_permute_extensions` вызывается
  безусловно, обёртки называют `--tls-permute-extensions` начиная с
  `curl_chrome120`, а захваты форка пишут `tls_permute_extensions: true` у всех
  Chromium ≥110. `ClientHelloProfile::permute_extensions` (флаг в пяти записях)
  повторяет это: тасуется копия порядка, зёрна — 128 бит из `SecureRandom`,
  расширения «обязательно последние» и GREASE-слоты остаются на местах.
  Замерено: два подряд запуска `curl_chrome136` дают разный порядок при одном
  размере, а `curl_chrome107` — побайтово одинаковые (контроль).
* **`zstd` в `compress_certificate`.** Firefox-семейство называет
  `--cert-compression zlib,brotli,zstd`, и тело расширения у бандла —
  `06000100020003`; теперь такое же у нас. Декодер — `ruzstd` 0.8 (MIT, 11 787
  строк, зависимости: `twox-hash`), с собственным потолком окна в 1 МиБ: у самой
  библиотеки `MAXIMUM_ALLOWED_WINDOW_SIZE = 100 МиБ`, что для 3–6 МБ бюджета
  недопустимо. Цена — **+61.5 КиБ** к релизному бинарнику (4 093 952 → 4 156 928
  байт), то есть +1.5 %.
* **ECH в форме GREASE.** Все девять записей с `--ech true`
  (`chrome120/131/131android/133/136`, `firefox`, `firefox135/144`, `tor145`)
  шлют `encrypted_client_hello` так же, как их обёртки: настоящего
  `ECHConfigList` у curl нет (нужен DoH или `--ecl:`), поэтому на провод уходит
  заготовка по §6.2 черновика. Реализация — `net/tls.rs` (`EchMode::Grease`) над
  новым `net/hpke.rs`: HPKE (RFC 9180) в базовом режиме, DHKEM(X25519,
  HKDF-SHA256) с HKDF-SHA256 и AES-128-GCM/AES-256-GCM/ChaCha20-Poly1305,
  проверенный векторами RFC (приложение A.1). Новых зависимостей нет: `x25519-dalek`,
  `aes-gcm`, `chacha20poly1305` и `hkdf` уже в графе через `rustls-rustcrypto`.
  Патчи rustls — ре-экспорт `HpkeKem`/`HpkeKdf`/`HpkeAead`/`HpkeSymmetricCipherSuite`,
  конструктор `HpkePrivateKey::from_bytes` и `with_ech_mode` (апстримный
  `with_ech` оставляет только TLS 1.3, а Chrome 120 шлёт и 1.2-набор). Цена —
  **+1 КиБ**.

Проверено: все девятнадцать профилей идут `liveany` на `cloudflare.com`,
`www.google.com`, `dns.google` и `tls.peet.ws` — `OK`, TLS 1.3, `h2`; у
`firefox` и `tor145` JA3 и JA4 совпали с бандлом (`2d692a4485ca…`/
`t13d1716h2_5b57614c22b0_eeeea6562960` и `0faf2a91198d…`/

Полный прогон `tools/fingerprint all` после этой правки:

* `echo-diff` — `SAME` у пятнадцати записей из девятнадцати, включая все четыре

  список заголовков. У пяти хромов расходятся только `tls.ja3` и `tls.ja3_hash` —
  перемешивание, которое и у бандла даёт новую строку на каждое соединение.
* `hello-diff` — у девяти записей с ECH остаётся `body ech` (тело пересобирается
  каждое соединение), а у пяти хромов ещё и `extensions DIFF`: обе стороны
  тасуют порядок, а `hello-diff` сравнивает списки как последовательности. То,

  выборка из распределения против одной выборки в захвате), у `chrome120` ещё
  `extensions, ja4` (тот же padding), у `tor145` — доли ключа (запись следует
  обёртке).
* `headers-diff` — все восемнадцать записей `SAME`.

Суммарно релизный бинарник вырос на **+72.7 КиБ** (4 093 952 → 4 166 656 байт,
+1.78 %): 61.5 КиБ — zstd, 1.0 КиБ — машина ECH, остальное — HPKE и тасование.

Что осталось, и почему это не закрыто:

* **настоящий ECH по конфигурации из DNS** — сознательно не делается (решение
  от 2026-09-18). Он бы делал hello зависимым от *хоста*, тогда как все
  остальные поля записи — от клиента, и обёртка его не шлёт; для диагностики он
  ничего не даёт (цензор не отличает GREASE-ECH от настоящего по построению), а
  стоит DNS-запроса в классифицируемом пути. Инфраструктура готова на две трети:
  `Hpke` написан и покрыт векторами RFC, `build_dns_query` принимает любой тип,
  неизвестные RR уже приезжают как `DnsRecord::Other` — нужны разбор HTTPS/SVCB
  и кэш конфигурации.
* **QUIC/HTTP-3** (M5) — тоже вне работы по решению от 2026-09-18: в
  `vendor/rustls-rustcrypto/src/quic.rs` четыре `todo!()`, у всех TLS 1.3-наборов
  `quic: None`; это отдельный план (§10).
* у `tor145` на одну долю ключа больше, чем у браузера в захвате форка (запись
  следует своей обёртке).

### Длина тела GREASE-ECH и имена обёрток (2026-09-18, второй проход)

**Длина тела ECH.** Тело GREASE-ECH собиралось кодированием внутреннего hello,
который этот клиент действительно послал бы, — 441 байт. У curl оно 186, 218, 250
или 282: BoringSSL не кодирует внутренний hello, а *оценивает* его в 128, 160, 192
или 224 байта (округление до 32 — гранулярность последнего шага padding реального
кодирования), выбирает одно из четырёх случайно и добавляет тег AEAD
(`setup_ech_grease()` в `ssl/encrypted_client_hello.cc`; арифметика сверена по
байтам четырёх запусков обёртки). Для цензора длина — стабильный признак сборки:
441 байт не шлёт ни один браузер. Теперь длину берём из тех же четырёх значений
(`vendor/rustls/src/client/ech.rs`), а `hello-diff` сравнивает не случайные байты,
а *объявленную* длину payload'а — тело любого другого размера он показывает как
расхождение. Регрессионный тест
(`the_ech_shapes_carry_the_grease_extension_and_the_others_do_not`) требует, чтобы
длина была одной из четырёх и чтобы за 16 соединений встретилось хотя бы две:
раньше он проверял только `payload_len > 16`, из-за чего 400-байтная полезная часть
и прожила проход.

**Padding под 512 байт — измерен, не воспроизводится.** Прошлый проход объяснял
расхождение `hello-diff` у `chrome120` «padding'ом, который бандл добавляет ниже
512-байтового порога» — и это была ошибка разбора: сравнивались *списки* как
последовательности, а обе стороны тасуют порядок, так что `extensions DIFF` был
про порядок, а не про набор. Пропущенным оказалось другое: `chrome120` и
`chrome131android` с самым коротким телом ECH доходят до 497 байт, и клиент
паддит их на 16 байт до 517 — а мы нет. Слот padding в записи воспроизвести
нельзя: `padding_to` профиля меряется до того, как rustls допишет типизированное
тело ECH (`msgs/handshake.rs`, `ClientExtensions::encode`), поэтому hello вырос до
803 байт против 517 у бандла. Шлётся вариант без padding — тот, который сам
клиент шлёт в трёх соединениях из четырёх, — и гэп описан как разница частоты, а
не формы (`net/fingerprint/mod.rs`, `tools/fingerprint/README.md`).

**Имена обёрток.** Форма каждой обёртки бандла сверена захватом через локальный
слушатель: `curl_chrome119`/`123` шлют hello Chrome 120, `curl_chrome142`/`145`/
`146` — Chrome 136, `curl_firefox147` — Firefox 144, поэтому эти имена теперь
разрешаются (`CurlNames`), а идентичность остаётся у записи — так же, как
`curl_chrome100…107` разрешались в 107-ю. Отвергаются по-прежнему
`curl_chrome110`/`116` (та же форма, но с перемешиванием, которого запись 107-й не
делает), `curl_chrome124` (формы нет ни у одной записи) и `curl_safari172_ios`
(iOS-идентичность без записи); список в доке `CurlNames`, README и тесте разбора
имён совпадает.

Полный прогон `tools/fingerprint all` после правки:

* `echo-diff` — `SAME` у тринадцати записей из восемнадцати, включая все четыре
  Firefox-строки и Tor; у пяти тасующих хромов расходятся только `tls.ja3` и
  `tls.ja3_hash` — перемешивание, которое и у бандла даёт новую строку на каждое
  соединение. JA4 совпал у всех, `chrome120` и `chrome131android` в том числе.
* `hello-diff` — `SAME` у тринадцати, включая четыре строки с ECH (`firefox`,
  `firefox135`, `firefox144`, `tor145`): тело сравнивается по объявленной длине,
  а не по случайным байтам. У пяти тасующих хромов остаётся `extensions DIFF` —
  это порядок; расхождение размеров теперь кратно 32 и равно разнице тел ECH

* `captures` — `SAME` у двенадцати; у пяти хромов `ext order`, у `chrome120` ещё
  `extensions, ja4` (в захвате форка hello с padding'ом — 19 расширений против

* `headers-diff` — все восемнадцать записей `SAME`, блок запроса совпал

Релизный бинарник не изменился: **4 166 656 байт** — вместо кодирования
